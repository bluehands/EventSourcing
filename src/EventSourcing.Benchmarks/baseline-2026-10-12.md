# Event-store performance baseline — October 2026

End-to-end measurements through the production event store, including serialization/deserialization, EF, and database I/O. These results describe local warm-cache workloads, not an engine-only comparison or a production capacity estimate.

## Workload

| Parameter | Value |
|---|---|
| Providers | SQLite, SQL Server Express, PostgreSQL |
| Scenarios | global, tail, stream, write, mixed |
| Seeded history | 10,000 events |
| Payload | 1,024 ASCII Data bytes/event, excluding JSON overhead |
| Streams | 10 |
| Workers | 1 and 4; mixed uses matching reader/writer counts |
| Write batches | 2, 100, 1,000 events, including a real CommandProcessed marker |
| Operations | 10 per worker per repetition |
| Repetitions | 2, with a separate one-operation/worker warmup per workload |
| SQL Server transfer | auto |

Global reads replay 10,000 events; tail reads cover the last 1,000; stream reads replay one seeded stream. Mixed readers replay seeded streams while writers append to separate streams. Reads are fully enumerated. Setup, seeding, warmup, and verification are excluded from timing. All measurements completed without operation failures, with read and persisted-write counts verified.

Each result contains 20 operations at one worker or 80 at four workers, per operation kind. Tail percentiles are directional: p99 is the maximum at these sample sizes. Mixed reader/writer groups may finish at different times, so contention need not persist throughout the run. See the [benchmark guide](README.md) for workload and measurement details.

## Reproduction

From the repository root, with `EVENTSOURCING_BENCHMARK_SQLSERVER` and `EVENTSOURCING_BENCHMARK_POSTGRES` configured:

```powershell
dotnet build src/EventSourcing.Benchmarks -c Release
dotnet run -c Release --no-build --project src/EventSourcing.Benchmarks -- --provider all --profile quick --scenarios global,tail,stream,write,mixed --workers 1,4 --batches 2,100,1000 --histories 10000 --payloads 1024 --streams 10 --operations 10 --repetitions 2 --command-batches --sql-transfer auto
```

## Environment

- Host: Windows 10.0.26300, x64, 16 logical processors. The October 12 run used .NET 10.0.12; the October 23 SQL Server Express run used .NET 10.0.13.
- SQLite 3.53.3: file-backed, WAL, synchronous=2 (FULL), page size 4,096; provider command timeout 30 seconds, PRAGMA busy_timeout=0.
- SQL Server Express: native Windows instance, SQL Server 2025 RTM, 17.0.1000.7, Express Edition x64. RCSI on, snapshot isolation OFF, read committed, SIMPLE recovery, delayed durability DISABLED.
- PostgreSQL 18.6: native Windows x64 server; read committed, synchronous_commit=on, fsync=on, full_page_writes=on, wal_level=replica, max_connections=100.

## Full aggregate results

R/W means readers/writers. Ops/s means committed appends/s for writes and complete enumerations/s for reads; write events/s includes completion markers. Throughput uses each group's active wall time. Latencies cover successful operations, including scope creation/disposal. Scaling compares event throughput with the matching one-worker reference (1 reader + 1 writer for mixed).
