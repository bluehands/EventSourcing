# Performance baseline — 2026-10-08

Release baseline: **126 measured repetitions, zero operation failures** on file-backed SQLite and SQL Server LocalDB. Read and persisted-write count checks passed. Total runtime: approximately **14 minutes**.

The [PostgreSQL native-writer baseline added on October 9](#postgresql-native-writer-baseline--2026-10-09) uses the same workload parameters and adds **63 measured repetitions, zero operation failures**.

## Parameters

```powershell
$env:EVENTSOURCING_BENCHMARK_SQLSERVER = 'Server=(localdb)\MSSQLLocalDB;Integrated Security=True;TrustServerCertificate=True'

dotnet run -c Release --project src/EventSourcing.Benchmarks -- --provider both --scenarios global,tail,stream --workers 1,4,8 --operations 20 --repetitions 3

dotnet run -c Release --project src/EventSourcing.Benchmarks -- --provider both --scenarios write --workers 1,4,8 --batches 1,10,100 --operations 1000 --repetitions 3

dotnet run -c Release --project src/EventSourcing.Benchmarks -- --provider both --scenarios mixed --workers 1,4,8 --batches 100 --operations 100 --repetitions 3
```

## Observations

- Parallel readers increased aggregate throughput on both engines. SQLite stream-read throughput plateaued at four readers.
- Batching substantially increased write throughput on both engines.
- SQLite write throughput stayed near the single-writer reference with four writers. With eight writers, batches 1 and 10 dropped to 0.39× and 0.28×; batch 100 retained 0.94×. The cause of the small-batch slowdown was not diagnosed.
- SQL Server parallel writes improved throughput for batches 1 and 10. Batch 100 peaked at four writers and returned near the single-writer reference at eight.
- Mixed batch-100 write throughput remained in the same range as concurrency increased, while aggregate read throughput increased.

## PostgreSQL native-writer baseline — 2026-10-09

**63 measured repetitions, zero operation failures.** Read and persisted-write count checks passed. Total execution time, including setup, seeding, warmup, verification and cleanup, was approximately **2 minutes 40 seconds**. All three runner-owned databases were removed, verified against `pg_database` after execution.

### Environment and parameters

Native PostgreSQL 18.6 on Windows x64, localhost port 5432; .NET runtime 10.0.12, 16 logical processors. Read committed, `synchronous_commit=on`, `fsync=on`, `full_page_writes=on`, `wal_level=replica`, `max_connections=100`; command timeout 30 seconds. Default Npgsql auto-preparation settings were used; auto-preparation was not enabled for this run.

Production writer: transaction-level advisory lock, bigint `CACHE 1 NO CYCLE` sequence, native typed-array insertion for ordinary appends and binary COPY for large transfers. These baseline batches (1/10/100 events with 1-KB data fields) use the array path; this run does not measure the COPY crossover. The provider owns each append transaction and holds the advisory lock through commit. EF reads and migrations remain in use.

The workload matches the original SQLite/SQL Server baseline: **10,000 seeded events, 10 streams, 1,024 ASCII data bytes/event, 1/4/8 workers, three repetitions**. Reads use 20 operations/worker, sustained writes use **1,000 appends/worker**, and mixed workloads use 100 operations/worker with batch 100. Unlike the earlier quick PostgreSQL runs, write duration and event growth parameters now match the original baseline. Each write operation is one committed batch; Ops/s means appends/s, not events/s. No command completion marker is automatically added by this direct `IEventStore` workload.

The run used Git HEAD `7634f0e433db93fc9b16183d809da4173bef5276` plus the uncommitted native PostgreSQL writer/schema and benchmark changes recorded in artifact metadata. SQLite/SQL Server results above remain the historical October 8 runs, recorded before correctness-review fixes. Matching workload parameters do not isolate database-engine differences across code revisions, server configurations, cache effects or system load.

### PostgreSQL observations

- Batch-100 write throughput was **49,599 / 82,888 / 81,612 events/s** at 1/4/8 writers, approximately **1.9–3.4×** the historical SQLite results and **2.8–4.8×** SQL Server. Four writers achieved the highest batch-100 throughput in this run.
- Mixed batch-100 writes reached **31,138 / 68,700 / 56,184 events/s** at 1/1, 4/4 and 8/8 readers/writers. Four/four throughput was about **4.0×** historical SQLite and **3.7×** SQL Server.
- Single-event writes reached **951 appends/s** with one writer, below both historical engines, and about **5,654 / 5,504 appends/s** with four/eight writers. The batch-10 single-writer workload was faster in appends/s than batch 1; workload ordering and runtime/server warmup can affect these fixed runs. The 5.94× four-writer scaling factor is relative to that slower single-writer reference, not evidence of superlinear allocator capacity.
- At eight readers, global replay reached **717,049 events/s**, below historical SQLite and above SQL Server. Stream reads reached **753,332 events/s**, roughly double both historical engines; tail reads remained below SQLite and above SQL Server.
- Compared with the earlier local EF/counter run, batch-100 write throughput increased from 20,692 to 49,599 events/s at one writer and from 22,632 to 82,888 at four. That earlier write run used only 100 appends/worker, so this is a contextual comparison rather than a matched before/after measurement.
